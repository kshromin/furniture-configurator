# DATA-SCHEMA.md — схема данных ассортимента (ЧЕРНОВИК v0.2)

> **Статус: ЧЕРНОВИК v0.2.** Сверено со структурой базы Базиса (`Config/Задания/база из базиса.xml`
> — материалы; `…рабочаяХромин.FDB` — полная схема по именам таблиц). Утверждено решение по
> архитектуре — **(А) единая база-суперсет** (см. ниже). Данные ещё НЕ мигрируем — это только
> контракт. Версия в поле `schema_version`. Правится вместе с [DEVLOG.md](DEVLOG.md) и планом
> `Config/Задания/первым делом.md`.

## Архитектурное решение (утверждено): (А) единая база-суперсет

- **Единая база материалов = источник правды** со ВСЕМ ассортиментом и стабильными ключами (как в
  Базисе). Не «отдельный файл на клиента россыпью» — надёжное хранилище (см. ниже про per-firm).
- **Каждое приложение берёт своё подмножество.** Конфигуратор не тащит все 3750+ позиций Базиса —
  он помечает, какие использует (`used_by`). Будущий калькулятор / экспортёр садятся на ту же базу.
- **Per-firm:** форма (эта схема) — общая для всех фирм; значения — свои (`companies.materials`,
  Supabase, RLS-изоляция). Экспорт по кнопке отдаёт каталог фирмы отдельным файлом для бэкапа/переноса.

## Зачем именно так

- **Переиспользование.** Другое приложение читает «список позиций по категориям», а не разбирает
  5 форматов. Прямо закрывает «задание единая база 31,07» (база для будущих мебельных приложений).
- **Калькулятор.** Цена = `количество × цена-за-единицу` → у каждой позиции ЯВНАЯ единица и цена.
- **Совместимость с Базисом** (индустриальный стандарт): общие ключи/поля → импорт/сверка/обмен.

## Принципы

1. **Позиционная модель.** Любая цена — строка `{ key, name, unit, price, attrs, … }`.
2. **Стабильный `key`** — наш машинный id (не меняется при переименовании; человекочитаемое в `name`).
3. **Внешние ключи `ext`** — id из других систем (Базис `Article`, `Sync_External`) для синхронизации.
4. **Явная единица** `unit` из контролируемого словаря (внешние «шт./компл/пог. м» нормализуем).
5. **Ручная цена** — маркер `"manual"` вместо числа (+ опц. `default`), единая механика для «спец/заказных».
6. **Справочники (`references`) отдельно от цен.**
7. **`group`** — путь-категория (совместимо с деревом Базиса) ПЛЮС наша канон. `category` (одна из 9).

## Словарь единиц (`unit`) + нормализация из Базиса

| код | смысл | варианты в Базисе, что схлопываем |
|---|---|---|
| `m2` | ₽/м² | `кв.м`, `кв.м.` |
| `m` | ₽/пог.м | `м`, `пог.м`, `пог. м`, `м.п` |
| `pc` | ₽/шт | `шт`, `шт.` |
| `set` | ₽/комплект | `компл`, `компл.`, `комплект` |
| `door` | ₽/дверь (авто 1 на купе-дверь) | — |
| `item` | ₽/изделие (авто 1 на изделие) | — |
| `kg`,`m3`,`l` | ₽/кг, ₽/м³, ₽/л *(из Базиса, на будущее)* | `кг`, `куб.м`, `л` |

## Универсальная позиция

```json
{
  "key": "ldsp.korpus.egger.h1277",        // наш стабильный id
  "ext": { "article": "16/EG-H1277  ST9", "sync": "" },  // ключи внешних систем (Базис)
  "name": "ЛДСП 16мм Акация Лэйклэнд светлая H1277",
  "category": "ldsp",                        // наша канон. категория (одна из 9)
  "group": "Листовой/EGGER 16мм",            // путь-категория (совместимо с Базис Group_Name)
  "unit": "m2",                              // из словаря единиц
  "price": 1925,                             // число ИЛИ "manual"
  "default": 3000,                           // опц.: дефолт для manual-позиции
  "attrs": {
    "producer": "egger", "color": "H1277",
    "sheet": { "l": 2800, "w": 2070, "t": 16 },  // размер листа — для раскроя/калькулятора
    "coef": 1.2                                   // коэффициент из Базиса (расход/наценка)
  },
  "hex": "#f4f3f0",                          // опц., если у позиции есть цвет
  "texture": "EGGER/H1277.jpg",              // файл текстуры (совместимо с Базис Texture, см. задание текстур)
  "used_by": ["configurator"],               // какие приложения используют позицию (для (А))
  "comment": ""                              // опц.
}
```

Обязательный минимум: `key, name, category, unit, price`. Остальное — по мере наличия.

## Категории (маппинг: как сейчас → целевая схема)

| Категория | Что сейчас в `materials.json` | ключевые `attrs` | `unit` | Заметки |
|---|---|---|---|---|
| `ldsp` | `korpus`/`fasad`/`fill`.producers[].colors[] | surface, producer, color, sheet, coef | `m2` | кромку выносим (см. `edge`) |
| `edge` | те же цвета: `edgePerM16/32` + legacy `edgeBanding` | ldspColorKey(ссылка), plate(16/32) | `m` | автосоздание на новый цвет ЛДСП |
| `door_fill` | `slidingDoor.fills` (mirror/glass/…) | kind, color | `m2` | «спец» = `manual` |
| `profile` | `slidingDoor.profilePrices` **(уже позиционно ✓)** | element, color | `m` | эталон формы (сессия 56) |
| `linear` | `meshShelf`, штанга | kind(mesh/rod), param, color | `m` | |
| `piece` | `basket`, `drawerSlide`, `fittings`(шт) | kind, params(w/d/h/length/type) | `pc`/`set` | |
| `hardware_auto` | `swingDoorHardware`, `fittings`(item) | trigger(per-door/per-item) | `door`/`item` | в смету автоматом |
| `addon` | `extras[].items` | group | `pc` | «заказная» = `manual` |
| `service` | (нет) | trigger, … | `door`/`item`/`m`/… | ⏸️ правила админа — см. «на будущее» |

## Справочники (`references`, не цены)

`palette` (цвета профилей `{name,hex}`) · `profile_colors` (`slidingDoor.colors`) · `valet_lengths` ·
`sizes.basket` / `sizes.mesh` (допустимые типоразмеры — ограничения выбора).

## Целевой контейнер верхнего уровня

```json
{
  "schema_version": "0.2",
  "categories": { "ldsp": [/*…*/], "edge": [/*…*/], "door_fill": [/*…*/], "profile": [/*…*/] },
  "references": { "palette": [/*…*/], "sizes": { "basket": [/*…*/] } }
}
```

1 категория ⇄ 1 файл/лист выгрузки (Этап 2); служебная колонка = `key` (+ `ext.article`); ручная
цена = слово `вручную`.

## На будущее: расчёт по количествам (НЕ техпроцесс)

Цель проекта — **быстрый расчёт цены по материалам и количеству** (кол-во × цена-за-единицу),
далее — по дизайн-проекту/сканам, опираясь на нашу базу. Это **НЕ производственная система**: мы не
конкурент Базис-Мебельщику, операции/техпроцесс/затраты **не моделируем** (см. память
`project-vision-roadmap`).

Поэтому из модели Базиса берём только **материалы** + `attrs.sheet`/`coef` (размер листа и
коэффициент — чтобы будущий калькулятор и расчёт по дизайн-проекту считали КОЛИЧЕСТВА, а не техпроцесс).
Пласт Базиса «операции/затраты» — вне проекта.

Позиционная модель при этом открыта к росту: при необходимости добавляются НОВЫЕ категории того же
вида (например, «услуги» с правилами админа — отложено), без пересборки контракта.

## Открытые вопросы

- Кромка ↔ цвет ЛДСП: ключ-связь `ldspColorKey`, автоген 16/32 при новом цвете.
- Механизм `used_by` / отметки «использует конфигуратор» — флаг на позиции или отдельный список выбора.
- `currency` / дата прайса на уровне контейнера (для калькулятора/экспорта).
- Формат правил «услуг» (админ задаёт) — при необходимости, отдельной категорией; не сейчас.

## Миграция (не ломать сразу)

Описана ЦЕЛЕВАЯ форма. Переносим по одной категории (план, Этап 1/2), экспорт пишем уже под неё,
регресс-проверка цены на каждом шаге. `profile` уже в целевой форме. Рекомендуемая первая категория
для переноса — **`edge` (кромка)**: и в плане отдельная, и проверит связку «позиция ↔ ссылка на цвет».

## Формат выгрузки/загрузки Excel (единый, с 4.08)

Шаблон пользователя — `Config/Выгрузки/шаблон.xlsx`. Решение: **категории = отдельные листы**
(вариант «А»), но набор и порядок колонок **одинаковый на всех листах**; неприменимое к категории
остаётся пустым. Порядок колонок менять нельзя — по нему читает `catalog_import.py`.

| # | Колонка | Смысл |
|---|---------|-------|
| 1 | Артикул/ид/key | стабильный ключ позиции (ВИДИМЫЙ; по нему загрузка находит позицию) |
| 2 | Производитель | бренд (у большинства категорий в базе не хранился — см. `catalogMeta`) |
| 3 | Название | что это (ЛДСП, Кромка, Стекло, «Открытый вертикальный», группа доп.элементов) |
| 4 | Цвет | цвет/исполнение/конкретная позиция группы |
| 5 | Ед.изм | кв.м / пог.м / шт / комплект / деталь / дверь / ящик… |
| 6 | **Цена** | жёлтая колонка; `вручную` = цену вводит пользователь при заказе |
| 7–9 | Высота / Длинна / Ширина, мм | габарит позиции |
| 10 | От чего зависит | ссылка на ключ (кромка → ключ ЛДСП) |
| 11 | Цвет (hex) | для показа |
| 12–14 | Корпус / Фасад / Наполнение | да/нет — где доступен материал (ЛДСП) |
| 15 | Файл текстуры | вид ЛДСП (сохранено из прежнего формата, в шаблоне не было) |

**`catalogMeta`** (новый ключ верхнего уровня в `materials.json`): `{ "<ключ позиции>":
{producer, h, l, w, dep, hex} }` — поля, которых в базе нет (производитель неплитных категорий,
габариты листа/хлыста, зависимость). В первой выгрузке пустые: пользователь заполняет в Excel,
загрузка сохраняет. Приложение эти поля не читает — это справочные данные каталога.

**Выводимые из позиции поля** (`DERIVED` в `catalog_export.py`) в `catalogMeta` не пишутся, потому
что следуют из самой позиции и вернутся при следующей выгрузке: толщина плиты ЛДСП/кромки (высота),
длина направляющей, размеры корзины, глубина сетчатой полки (ширина), hex профиля/материала —
они правятся прямо в базе (ключ тот же = та же позиция, см. ниже).

### Ключ = стабильный id позиции (задание «формат выгрузки», 5.08)

Правило одно и **действует на все категории**: пока в строке стоит тот же ключ — это та же позиция,
и правка **любого** столбца (название, цвет, размер, производитель, цена) обновляет её, дубля не
возникает. Строка без ключа = новая позиция (на листах, где создание разрешено, см. `CREATORS`).

Чтобы это работало у категорий, где ключ раньше собирался из атрибутов, позиции получили поле
**`gid`** — стабильный id, который не меняется при правке атрибутов:

| Категория | Ключ | `gid` выводится из |
|---|---|---|
| ЛДСП | `ldsp:<gid>` | `<id производителя>__<id цвета>` (общий для корпуса/фасада/наполнения) |
| Сетчатые полки | `mesh:<gid>` | `<глубина>_<цвет>` |
| Корзины | `basket:<gid>` | `<ширина>_<глубина>_<высота>_<цвет>` |
| Направляющие | `slide:<gid>` | `<тип>_<длина>` |

`gid` проставляется загрузкой (`ensure_gids`) и выводится детерминированно из тех же полей, из
которых раньше собирался ключ, — поэтому **старые выгрузки грузятся без потерь** (ключ
`mesh:300:white` = `gid` `300_white`). Если правка сделала позицию неотличимой от другой (те же
размер+цвет), загрузка останавливается с ошибкой — дубль в каталоге не создаётся.

**Макс. размер детали (ЛДСП).** Колонки «Длинна»/«Ширина» на листе ЛДСП = максимально допустимый
размер детали из этого материала; хранятся в самом материале — `maxPartL` / `maxPartW` (мм) у
каждого его члена (корпус/фасад/наполнение синхронно, по `gid`), а не в `catalogMeta`: это свойство
материала, которое понадобится раскрою/калькулятору. Пустая ячейка = ограничения нет (поля просто
отсутствуют). Нечисловое значение останавливает загрузку. Приложение их пока не читает.

**`catalogLabels`** (ключ верхнего уровня): названия позиций, у которых в базе нет поля имени —
направляющие (`slide:<gid>`) и общие элементы профиля (`profel:horizTop|horizBottom|divider|track`).
Переопределение хранится только если отличается от типового названия. Приложение не читает.

Правка полей, **общих для нескольких строк** (цвет профиля и его hex — в каждой строке листа
«Профили купе»; раздел в «От чего зависит» — в каждой строке своей группы), применяется только из
тех ячеек, которые реально изменились: загрузка сравнивает строку с тем, как она выглядела в
выгрузке (`build_baseline`). Иначе соседние строки с прежним значением затирали бы правку.

### Две таблицы на листе: не добавляемые / добавляемые (5.08)

Листы «Фурнитура», «Услуги», «Доп.элементы» разделены серой строкой-заголовком (первая ячейка
начинается с `#`, загрузка такие строки пропускает):

- **НЕ ДОБАВЛЯЕМЫЕ** (сверху) — позиции, заведённые в самой программе: она обращается к ним по id
  и считает по своим правилам, поэтому их нельзя ни добавить, ни удалить из Excel. У них правится
  **только цена** — единственное исключение из правила «правь любой столбец» (`FIXED_PRICE_ONLY` в
  `catalog_import.py`). Это `fittings`, `swingDoorHardware`, ролики, труба, доводчик, ручка ящика,
  а на листе услуг — `services` (Крепёж, Встройка).
- **ДОБАВЛЯЕМЫЕ** (снизу) — ассортимент, который ведёт пользователь. Раздел позиции задаётся
  колонкой **«От чего зависит»** («Ручки ящика», «Монтаж», «Доставка»…): новая строка со знакомым
  разделом добавляет в него позицию, с новым — заводит раздел. «Название» = сама позиция.

**`extras[].kind`** = `service` | `extra` — на какой лист идёт группа: услуги (Доставка, Подъём на
этаж, Монтаж) или доп.элементы. Проставляется загрузкой (`DEFAULT_SERVICE_GROUPS` — дефолт для
групп, заведённых до этого правила); у новых групп — по листу, на котором их создали. Приложение
`kind` не читает: в интерфейсе «Добавить к заказу» группы по-прежнему в одном списке.

**`fittingOptions`** (новый ключ верхнего уровня): `[{gid, group, name, unit, price}]` — добавляемая
фурнитура по разделам, `unit` только `шт|комплект|пог.м`. Заполняется через нижнюю таблицу листа
«Фурнитура». Приложение пока её не читает: выбор фурнитуры по разделам — отдельная задача, до неё
это наполнение каталога.
