# DATA-SCHEMA.md — схема данных ассортимента (ЧЕРНОВИК v0.1)

> **Статус: ЧЕРНОВИК.** Цель — единый, самоописательный формат данных ассортимента, пригодный не
> только для конфигуратора, но и для будущих приложений (калькулятор цены по количеству, экспорт в
> другие программы, обмен с Базисом). Ждёт **выгрузку из Базиса** для сверки полей и совместимости.
> Версионируется полем `schema_version`. Правится вместе с [DEVLOG.md](DEVLOG.md) и планом
> `Config/Задания/первым делом.md` (Яндекс).

## Зачем именно так

- **Переиспользование.** Другое приложение (калькулятор, витрина, экспортёр) читает «список позиций
  по категориям», а не разбирает 5 разных форматов, как сейчас.
- **Одна форма — свои значения.** У всех фирм ОДНА эта схема; значения (цены/цвета) у каждой свои
  (хранятся в `companies.materials`, см. [SUPABASE-SETUP.md](SUPABASE-SETUP.md)). Завёл фирму →
  свой каталог той же формы.
- **Калькулятор.** Цена = `количество × цена-за-единицу`. Значит у каждой позиции нужна ЯВНАЯ
  единица и цена за неё — тогда сторонний расчётчик садится на данные без «переводчиков».

## Принципы

1. **Позиционная модель.** Любая ценовая позиция — строка с полями `{ key, name, unit, price, attrs }`.
2. **Стабильный `key`** — машинный id, по нему импорт находит позицию; НЕ меняется при переименовании
   (человекочитаемое — в `name`).
3. **Явная единица** `unit` у каждой позиции (см. словарь ниже).
4. **Ручная цена** — маркер `"manual"` вместо числа (+ опц. `default`), единая механика для всех
   «спец/заказных» позиций (сейчас так только у спеццвета стекла).
5. **Справочники (`references`) отдельно от цен** — палитры, допустимые размеры это НЕ позиции.
6. Значения — per-firm; **форма — общая** и стабильная.

## Словарь единиц (`unit`)

| код | смысл | пример |
|---|---|---|
| `m2` | ₽/м² | ЛДСП, зеркало, стекло |
| `m` | ₽/пог.м | профиль, кромка, сетчатая полка, штанга |
| `pc` | ₽/шт | корзина, комплект направляющих |
| `set` | ₽/комплект | крепёж на изделие |
| `door` | ₽/дверь (авто 1 на купе-дверь) | сборка двери, фурнитура распашной |
| `item` | ₽/изделие (авто 1 на изделие) | крепёж/доводчики |

## Универсальная позиция

```json
{
  "key": "ldsp.korpus.egger.w980",   // стабильный id, уникален в категории
  "name": "Белый альпийский",          // человекочитаемо
  "unit": "m2",                        // из словаря единиц
  "price": 900,                        // число ИЛИ "manual"
  "default": 3000,                     // опц.: дефолт для manual-позиции
  "attrs": { "surface": "korpus", "producer": "egger" },  // специфично для категории
  "hex": "#f4f3f0",                    // опц., если у позиции есть цвет
  "comment": "..."                     // опц.
}
```

## Категории (маппинг: как сейчас → целевая схема)

| Категория | Что сейчас в `materials.json` | `attrs` | `unit` | Заметки |
|---|---|---|---|---|
| `ldsp` | `korpus`/`fasad`/`fill` → `producers[].colors[].pricePerM2` | `surface`(korpus/fasad/fill), `producer`, `color` | `m2` | цвет несёт ещё и кромку — выносим (см. `edge`) |
| `edge` | в тех же цветах `edgePerM16/32` + legacy `edgeBanding.pricePerM` | `ldspColorKey`(ссылка), `plate`(16/32) | `m` | автосоздаётся на каждый новый цвет ЛДСП; развязать с `ldsp` |
| `door_fill` | `slidingDoor.fills` (mirror/glass/…) | `kind`(mirror/glass/…), `color` | `m2` | «спец» = `manual` |
| `profile` | `slidingDoor.profilePrices` **(уже позиционно ✓)** | `element`, `color` | `m` | ЭТАЛОН формы — уже сделано (сессия 56) |
| `linear` | `meshShelf`, штанга | `kind`(mesh/rod), `param`(depth…), `color` | `m` | |
| `piece` | `basket`, `drawerSlide`, `fittings`(per=item→шт) | `kind`, `params`(width/depth/height/length/type) | `pc`/`set` | |
| `hardware_auto` | `swingDoorHardware.pricePerDoor`, `fittings`(per=item) | `trigger`(per-door/per-item) | `door`/`item` | добавляется в смету автоматически |
| `addon` | `extras[].items` | `group` | `pc` | «заказная» = `manual` |
| `service` | (пока нет) | `trigger`, … | `door`/`item`/`m`/… | ⏸️ ОТЛОЖЕНО: нужны настраиваемые правила админа, не хардкод |

## Справочники (`references`, не цены)

| Ключ | Сейчас | Смысл |
|---|---|---|
| `palette` | `palette` `[{name, hex}]` | палитра цветов профилей |
| `profile_colors` | `slidingDoor.colors` | цвета профилей купе |
| `valet_lengths` | `valetLengths` | допустимые длины вешала |
| `sizes.basket` / `sizes.mesh` | из `basket`/`meshShelf` | допустимые типоразмеры (ограничения выбора) |

## Целевой контейнер верхнего уровня

```json
{
  "schema_version": "0.1",
  "categories": {
    "ldsp": [ /* позиции */ ],
    "edge": [ /* позиции */ ],
    "door_fill": [ /* … */ ],
    "profile": [ /* … */ ]
  },
  "references": {
    "palette": [ /* … */ ],
    "sizes": { "basket": [ /* … */ ] }
  }
}
```

Соответствие **9 файлам выгрузки** (Этап 2 плана): 1 категория ⇄ 1 файл/лист; служебная колонка =
`key`; ручная цена = слово `вручную`.

## Открытые вопросы (сверить, в т.ч. с Базисом)

- **Кромка ↔ цвет ЛДСП:** ключ-связь `ldspColorKey`, автогенерация 16/32 при новом цвете.
- **Услуги/сборка:** формат правила (`per-door` / `per-item` / `per-section` / `per-m фасада`),
  задаёт **админ**, без хардкода. Проектируется отдельно.
- **Совместимость с Базисом:** ждём выгрузку — подогнать имена полей/ключей, где разумно.
- **Производитель** как отдельная сущность/справочник (для фильтров в сторонних приложениях)?
- Нужен ли `currency`/дата прайса на уровне контейнера (для калькулятора/экспорта).

## Миграция (не ломать сразу)

Здесь описана ЦЕЛЕВАЯ форма. Переносим по одной категории (план, Этап 1/2); экспорт пишем уже под
неё. `profile` уже в целевой форме. Пока приложение читает `data/materials.json` в старом виде —
рефакторинг покатегорийный, с регресс-проверкой цены на каждом шаге.
