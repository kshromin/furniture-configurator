# Конфигуратор мебели

Параметрический 3D-конфигуратор мебели (Three.js) — статический сайт, без сборки. Открывать через `preview_start` (конфиг `static` в `.claude/launch.json` КОРНЯ Config, порт 8723; сервер сам раздаёт эту папку, откуда бы ни стартовал).

## Где что лежит и как синхронизируется (схема с сессии 45)

- **Код** (эта папка, git-репозиторий) — отдельной папкой ВНЕ Яндекс.Диска: `config_comp` на
  компе, `config_nout` на ноуте. Между машинами едет ТОЛЬКО через GitHub (`git pull`/`push`);
  Яндекс код не синхронизирует и потому не может испортить `.git`. (Если код ещё внутри Яндекса —
  разовая настройка «вынести» описана в [GIT-SYNC.md](GIT-SYNC.md).)
- **Материалы** пользователя (Задания, Выгрузки, Бэкапы, Ассортимент…) — на Яндекс.Диске, папка
  `Config`. Их синхронизирует Яндекс, git их не касается, на сайт они не попадают.
- **Файлы материалов в чате** — подключать через `/add-dir <путь к папке материалов на Яндексе>`:
  основная папка сессии = код, добавленная = материалы; так читаю/пишу ассортимент, скрипты,
  выгрузки без копипаста в чат. Имя папки кода (`config_comp`/`config_nout`) заодно показывает, на
  какой машине идёт работа.
- **База знаний по системам купе** — ОТДЕЛЬНЫЙ репозиторий `C:\KB_KUPE`
  (`github.com/kshromin/kupe-kb`, приватный; на комп ставится через `git clone`, на Яндекс НЕ
  кладётся — Яндекс портит `.git`). Там формулы расчёта дверей, наполнения и профилей по
  каталогам производителей, предельные размеры, палитры декоров, оригиналы каталогов, плюс
  скиллы `kupe-kb` и `door-sizing` (ход работ по размерам дверей). В этом репозитории таких
  знаний нет намеренно: базой будут пользоваться и калькулятор, и выгрузки, не только
  конфигуратор.

  Нужны размеры дверей купе, профилей, наполнения или цвета профиля — подключить базу:
  ```
  /add-dir C:\KB_KUPE
  ```
  Считать по числам из кода конфигуратора нельзя: они упрощённые и с каталогом расходятся,
  это и есть предмет незаконченной работы (см. скилл `door-sizing` в базе).

При старте работы в этой папке:
1. Прочитать [DEVLOG.md](DEVLOG.md) — журнал сессий (что менялось и почему), даже если не попросили явно.
2. Если что-то в git-состоянии выглядит непривычно (`git pull`/`push` ведут себя не так, как ожидалось) — см. [GIT-SYNC.md](GIT-SYNC.md).
3. [STRUCTURE.md](STRUCTURE.md) — карта файлов проекта (что где лежит). Держать в актуальном состоянии: любое изменение структуры (новый файл, разбивка/слияние/переименование модуля, смена ответственности между файлами) — сразу отражать там же, в рамках той же сессии, не откладывая.

## Рабочий процесс (правила от пользователя, сессия 25)

- **Работаем по блокам**: типы изделий делаются ПО ОДНОМУ (сейчас — шкаф-купе). Кнопки
  не начатых типов заблокированы с подписью «в разработке» — белый список `READY_TYPES`
  в `js/core/tabs.js` (включить новый тип = добавить его id туда + убрать фильтр шаблонов
  в `js/core/presets.js`).
- **Коммитить** — локально по завершении фичи (без вопросов), это дёшево и спасает историю.
- Экономить токены: не перечитывать большие файлы целиком, грепать точечно; STRUCTURE.md —
  карта, DEVLOG.md — контекст сессий.

### Команды «старт» и «финиш»

Сайт пока ТЕСТОВЫЙ (в нём никто не работает), поэтому публикация не страшна — пушим свободно,
ветку work/main не разводим (вернёмся к разделению, когда появятся реальные клиенты).

**Где что живёт (с 09.08.2026):** конфигуратор — `mebel.khrom-in.ru`, база и вход —
`api.khrom-in.ru`, сайт — `project.khrom-in.ru`; всё на своём сервере Selectel (Москва),
подробности и порядок работ — в [deploy/README.md](deploy/README.md). Старый `config.khrom-in.ru`
заморожен на GitHub Pages со старой облачной базой — на нём не работать, изменения туда не попадут.

**«Старт»** (он же «начали»/«поехали») — начало сессии на любой машине:
1. `git pull` — подтянуть всё новое с GitHub (код и DEVLOG) в локальную папку.
2. Прочитать DEVLOG.md для контекста.
3. Проверить, нет ли в DEVLOG висящей записи «НАЧАТА» без завершения с ДРУГОЙ машины. Если есть —
   ПРЕДУПРЕДИТЬ пользователя: там сессию начинали, но не закончили, могут быть незапушенные
   правки; дождаться его решения, прежде чем работать.
4. Добавить запись «## <дата> — сессия N (<машина>) — НАЧАТА <время>» (машина — из имени папки
   `config_comp`/`config_nout`), закоммитить и `git push` — чтобы вторая машина видела открытую
   сессию.
5. Если нужны материалы — подключить их папку через `/add-dir`.

**«Финиш»** (он же «закончили»/«всё») — конец сессии, без дополнительных вопросов:
1. Дописать тело записи сессии в DEVLOG.md (что сделано и почему), сменив статус «НАЧАТА» на
   завершённую.
2. Закоммитить все изменения (осмысленными коммитами, как в остальной истории).
3. Запушить на GitHub (`git push`).
4. **Выложить на боевой сервер**, если менялся код сайта: `bash deploy/deploy.sh`. Пуш сам по себе
   больше ничего не публикует — с 09.08.2026 конфигуратор живёт на своём сервере
   (`mebel.khrom-in.ru`), а не на GitHub Pages. Забыли выложить — на сайте останется старая версия.

Связка: всегда «финиш» перед уходом с машины + «старт» на другой — тогда работа не теряется и не
расходится. Всё ценное должно попасть в репозиторий: код — коммитом, контекст — записью в DEVLOG;
что осталось только в переписке чата, для других машин не существует.
